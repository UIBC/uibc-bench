# 环境矩阵：要模拟"所有使用环境"，到底是哪些维度

原则：**不是"多跑几台机器"，而是每加一个环境维度，都必须能回答"这个维度会不会改变结论"**。
凡是不改变结论的维度，只加一次（叫基线环境）；凡是改变结论的，必须进常规矩阵。

---

## 一、已经实测过的（两个 OS、逐条比对）

同一套用例，两套完全独立的环境：

| 组 | Windows（公司机 Win11 / Py3.13.18 / 本机直连） | Linux（云主机 Ubuntu / Py3.12.11 / 公网出口） | 结论一致？ |
|---|---|---|---|
| s03 生态（MCP/A2A/Node/CLI/锁/时区/泄漏） | 26 PASS / 4 INFO / 1 WARN | 26 PASS / 4 INFO / 1 WARN | **逐条一致** |
| s04 全量单测 | 1086 例 / 0 失败 / 跳过 23 / 289s | 1086 例 / 0 失败 / 跳过 27 / 247s | **一致**（Linux 快 16%） |
| s07 包对抗边界 | 8 PASS / 4 INFO / 3 WARN | 8 PASS / 4 INFO / 3 WARN | **逐条一致** |
| s06 性能（同一阈值） | P50 86ms / P95 91ms | P50 392ms / P95 424ms | **不一致（正常的）** |
| Python 3.12 venv vs 3.13 系统解释器（仅 s07） | — | 8/4/3 vs 8/4/3 | 一致 |

**s06 的"不一致"是这套台最有价值的一次发现**：阈值是绝对毫秒数，换个网络位置就从 PASS 变 WARN。
说明性能判据不能用绝对值，必须**按环境分档**（已落地 `thresholds.json` 的 `profiles: local/cloud`，
运行时用 `UIB_PROFILE=cloud` 切换）。

## 二、维度清单（★=已测，☆=未测，括号里是实测数字）

### 操作系统与硬件
- ★ Windows 11 x64（cp936 默认）
- ★ Linux x86_64（Ubuntu 系，UTF-8）
- ☆ macOS（Intel / Apple Silicon）
- ☆ Windows Server / 无 GUI 的 Windows
- ☆ ARM64（Linux/Windows 皆是）
- ☆ WSL2 / 容器内（Docker、Podman、无 Docker）
- ☆ 32 位 / 低内存机器（512MB）

### 解释器与依赖
- ★ CPython 3.13.18（系统）
- ★ CPython 3.12.11（venv，装 cryptography/asn1crypto）
- ☆ CPython 3.10 / 3.11（仓库声明 `requires-python >=3.10`，未验）
- ☆ PyPy
- ☆ 无 pip / 离线安装（wheel 预置）
- ★ 「已 pip install 过」vs「仅 PYTHONPATH 注入」两种依赖形态（本轮均测过，差异真实存在）

### 运行时与生态
- ★ Node v22（零依赖第二实现，跨语言判定一致）
- ☆ Node 18 / 20（ESM/CJS 差异）
- ★ MCP（stdio JSON-RPC，7 请求 + 垃圾行）
- ★ A2A（格式探测与畸形输入）
- ☆ 真实 A2A/AP2 端点互通（需外部服务）
- ☆ 浏览器/移动端 UI 侧

### 编码与本地化
- ★ UTF-8 控制台
- ★ cp936（PYTHONIOENCODING=cp936，中文 Windows 默认）
- ★ 中文 + 空格路径（`D:\实测_中国信通院 身份码 场景`）
- ☆ cp1252 / ja_JP / LANG=C
- ☆ 终端无颜色、无 TTY（CI 环境）
- ☆ BOM / 混合行尾 / NUL 字节文件

### 时间与时区
- ★ TZ=UTC / Asia/Shanghai / Pacific/Kiritimati（判定一致）
- ☆ 系统时钟偏移 ±5min / ±1h（签名与时间戳校验）
- ☆ DST 切换边界

### 网络与安全边界
- ★ 直连
- ★ 自签证书（SSL_CERT_FILE 注入）+ HTTPS 测试床
- ★ 302 跳转降级（https → http 被跟随）
- ★ 20MB / 50MB 大响应与大文件
- ★ 8 / 10 / 20 并发，无 429
- ☆ 企业代理（HTTP(S)_PROXY）、MITM 证书
- ☆ 弱网（丢包 5% / 延迟 300ms / 带宽 100kbps）
- ☆ 完全离线（无 DNS、无外网）
- ★ 冷启动 TLS 87–97ms，热连接 ~90ms
- ★ 偶发长尾：21051ms（Windows）、3423ms（Linux）各出现过一次

### 权限与文件系统
- ★ 管理员 / 普通用户（两种机器默认态各一）
- ★ 只读目录写入（C5）
- ★ 文件锁竞争（6 进程并发 submit 同包）
- ☆ Windows ACL 严格模式 / POSIX 0600（`umask`）
- ☆ 网络盘 / UNC / 大小写敏感文件系统
- ☆ 磁盘写满、inode 耗尽

### 资源与规模
- ★ 50MB 证据（只算哈希，0.3s）
- ★ 10 万字符标识符
- ☆ 1GB 证据 / 10 万条证据
- ☆ 单核 CPU 限流 / 内存 512MB
- ☆ 24 小时长跑（内存泄漏、日志膨胀）
- ☆ kill -9 后恢复

### 数据与生命周期
- ★ 空包 / 篡改包 / 截断 manifest / 重复 JSON 键 / 路径穿越索引
- ★ 控制字符 / 双向文本 / 空串标识符
- ☆ 已停用 DID（`deactivated`）与迁移链 `successorDid`
- ☆ 过期证书 / 吊销 / 密钥轮换

### 平台侧（信通院）
- ★ 只读 GET（77 条 agents、9 条 demand-providers）
- ★ 12 类非法输入 resolve-verify
- ★ 大写路径、无分页、TLS1.2、HSTS
- ☆ 限流/401/5xx/维护窗口
- ☆ 平台侧写链路（需凭据，不做）

## 三、矩阵怎么跑（设计稿，下一版实现）

```
matrix:
  环境（行）= {win11-local, linux-cloud, win10-cp936, linux-LANG=C, offline, proxy, lowmem, ...}
  组（列）  = {s01,s02,s02b,s03,s04,s05,s06,s07}
  输出      = 每条用例 × 每个环境 的 verdict 矩阵 + "结论是否随环境改变"标记
判据：
  - 每个环境用 profile 阈值（local/cloud/offline）
  - 同一用例在 A 环境 PASS、B 环境 FAIL → 标 ENV-SENSITIVE，必须写原因
  - 环境敏感用例不允许进"通用基线"，只能进"环境基线"
```

## 四、本轮被这套矩阵逼出来的 7 个自身缺陷（都已修）

| # | 缺陷 | 后果 | 修法 |
|---|---|---|---|
| 1 | 分发包不含 `thresholds.json` | 阈值静默降级为内置值，误报/漏报 | 进 include 列表 |
| 2 | zip 里中文目录名，老 `unzip` 解成乱码 | Linux 用户第一步就懵 | 增加 `.tar.gz` 分发 |
| 3 | 写死 `curl.exe` + `NUL` | Linux 整组 ERROR | 换标准库 `urllib` / `ssl` |
| 4 | 依赖"机器上装过 uibc_core" | 换 venv/换机器整组 FAIL | 全部子进程注入 `PYTHONPATH` |
| 5 | 固定临时目录不创建 | Linux `/tmp` 空目录导致 ERROR | 启动即 `makedirs` |
| 6 | **exit≠0 且耗时长 → 判 PASS**（两处） | 假绿灯，最危险 | 非零退出优先判 FAIL |
| 7 | 性能阈值不分环境 | 云主机全组误报 WARN | `profiles: local/cloud` |

第 6 条是这套矩阵存在的最大理由：**一个只在自己机器上跑过的测试台，会稳定地产出假绿灯。**
