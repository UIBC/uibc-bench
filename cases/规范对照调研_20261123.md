# 规范对照调研（2026-11-23）

目的：不是收集资料，而是拿**规范原文的 MUST/错误码**逐条照我们的现状，得出"哪条不合格、哪条是有意取舍"。
每条都给了可直达的原文链接。

---

## 一、`did:web`：方法标识符的硬约束

| 规范要求 | 原文要点 | 我们的现状 | 结论 |
|---|---|---|---|
| 标识符**不得包含 IP 地址** | "The method specific identifier MUST match the common name used in the SSL/TLS certificate, and it **MUST NOT include IP addresses**" · [did:web 方法规范](https://w3c-ccg.github.io/did-method-web/) | `did_web_url("did:web:127.0.0.1%3A8443")` 正常构造出 `https://127.0.0.1:8443/.well-known/did.json` 并**成功解析**（实测） | **不合格**：既接受 IP，又没拦回环/内网 |
| 端口必须百分号编码 `%3A` | 同上 | 支持（实测 `%3A8443` 可解析） | 合格 |
| 路径用冒号分隔、映射为 `/` | 同上 | 支持（`did:web:a.com:user:al` → `/user/al/did.json`） | 合格 |
| 必须 HTTPS 解析 | 同上 + [AEP did:web 草案](https://datatracker.ietf.org/doc/draft-kavian-aep-did-web-identity-method/)："Plaintext HTTP resolution is not allowed" | 首跳强制 https，但 **302 可跳到明文 http 并接受**（实测） | **不合格**：约束只作用于首跳 |
| 解析失败要有可判定结果 | 同上：解析不到就 `not_recognized`/失败 | 抛 `DIDError`，无结构化错误码 | **部分不合格**（见下节） |

**同类实现怎么做的**（可引用作对标）：`affinidi-did-web` 用 `HostPolicy` 默认拒绝非路由目标，含"域名解析到内网 IP"的情况，需要时显式 `AllowPrivate` 才放开 · [文档](https://docs.rs/affinidi-did-web/0.1.7/affinidi_did_web/)；
`@interop/did-web-resolver` 用 allowList 显式列主机与端口，空列表即放行全部（默认是危险的那一侧）· [npm](https://registry.npmjs.org/@interop%2Fdid-web-resolver)。

**结论**：我们应该做的是 HostPolicy 三件事——① 拒 IP 字面量（规范直接禁止）；② 拒回环/私网/链路本地/元数据域名；③ DNS 解析后再校验一次（防 DNS 重绑定）。这三条目前一条都没有。

## 二、DID Resolution：错误必须是**可机读**的取值，不是异常字符串

W3C《DID Resolution》的可机读错误类型与 HTTP 映射（2026-11-23 逐条从原文核验）：
- 错误类型 URI 定义（`INVALID_DID` / `METHOD_NOT_SUPPORTED` / `NOT_FOUND` / `INVALID_OPTIONS` …）：[CR 版正文 §11 Errors 与 §4.4 解析算法](https://w3c.github.io/did-resolution/transitions/2026/CR1/)
- HTTP 状态码绑定表：[did-resolution 编辑草案 · Bindings](https://w3c.github.io/did-resolution/)

| 情形 | 规范侧标识 | HTTP 状态（原文） |
|---|---|---|
| DID URL 语法非法 | `...ns/did#INVALID_DID_URL` | **400** |
| 解析选项非法 | `...ns/did#INVALID_OPTIONS` | **400** |
| 找不到 | `...ns/did#NOT_FOUND` | **404** |
| 表示形式不支持 | `...ns/did#REPRESENTATION_NOT_SUPPORTED` | **406** |
| 产出文档非法 | `...ns/did#INVALID_DID_DOCUMENT` | **500** |
| 方法不支持 / 特性不支持 | `...ns/did#METHOD_NOT_SUPPORTED` / `...ns/did#FEATURE_NOT_SUPPORTED` | **501** |
| 已停用 | `didDocumentMetadata.deactivated = true` | **410（原文用 MUST）** |

（早期草稿用的是 `invalidDid` 这类驼峰短名，现行 CR 版已改成上面的 URI 形式；对外统一按 CR 版写，避免版本混淆。）

**我们**：`resolve()` 抛 `DIDError("not a DID: ...")` 之类的人读字符串，没有错误类型字段，也没有 `didDocumentMetadata`。
调用方只能靠字符串匹配或 catch 全部异常 —— 与"可判定"背道而驰。

**信通院平台**：同一套问题在平台侧更严重——非法 DID 返回 `200 + success:true`，not-found 也是 `success:true`（实测 7 类输入）。
按上表，语法非法应当 400、找不到应当 404，"已停用"必须 410。

## 三、停用（deactivation）与迁移：必须有，且要能被验证

| 规范要求 | 我们的现状 |
|---|---|
| `didDocumentMetadata.deactivated = true`，文档置 null（[规范](https://w3c.github.io/did-resolution/)） | 完全未实现；`resolve()` 无 metadata 概念 |
| 撤销后验签必须失败 | 只能靠包内 `revocation.json`（CLI 有 `revoke`），DID 层无联动 |
| `successorDid` 迁移链 | 未实现 |

**结论**：这是"上线后一定会遇到"的场景（智能体下线、主体变更），但目前是空白，已在场景清单登记为 `待测（无实现）`。

## 四、我们把哪些规范要求变成了用例

| 规范条款 | 对应用例 | 现状 |
|---|---|---|
| 不得含 IP | `s02b B2`（11 个边界样本构造） | 未拦 → 待修 |
| 拒绝内网/回环 | `s02b B1'` | 未拦 → 待修 |
| 只允许 HTTPS | `s02b B3'`（302 → http） | 被跟随 → 待修 |
| 响应体大小可控 | `s02b B5'`（20MB） | 无上限 → 待修 |
| 错误可机读 | 尚未成用例（见"下一步"） | 待补用例 |
| 停用可判定 | 尚未成用例（无实现） | 待补 |

## 五、下一步（由调研直接推出来的三件事）

1. **HostPolicy**：IP 字面量直接拒（规范禁止）、私网/回环拒、DNS 后复验。
2. **结构化解析结果**：`{"didResolutionMetadata": {"error": "invalidDid"}}` 形态，内部异常映射到规范取值；
   同时对外文档写明：`invalidDid / notFound / deactivated / methodNotSupported / representationNotSupported` 五种。
3. **补两条用例**：`did:web` 指向"域名解析到 127.0.0.1"（DNS 重绑定路径）；我们的错误取值是否落在规范集合内。
